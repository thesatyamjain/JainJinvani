## 2024-05-23 - Debouncing Search Overlay Queries
**Learning:** In the `SearchOverlay` component, filtering content directly on every keystroke (`query`) blocks the main thread because the calculation of `categoryCounts` and `filteredItems` are synchronous and depend directly on the query state. This leads to input lag and UI stuttering on low-end devices.
**Action:** Debounced the search `query` value and replaced instances of `query` in heavy operations (like `categoryCounts`, `filteredItems` and complex UI logic) with `debouncedQuery`. This allows the input state to update instantly while deferring expensive operations to slightly later, making the UI feel smoother.
## 2024-05-24 - Redundant Recalculations in Tabbed Overlays
**Learning:** In components with multiple sub-views or filter tabs (like `SearchOverlay.tsx`), executing heavy operations (like filtering or sorting) inside dependent `useMemo` blocks (like `categoryCounts` and `filteredItems` separately) creates overlapping redundant computations. If they share the same source pool and logic, the underlying operation (like `searchAndRankItems`) gets executed multiple times redundantly (N times the dataset) when state shifts.
**Action:** Lift the heavy operation into a single, centralized `useMemo` block that runs *once* per dependency trigger (like `debouncedQuery`). Then, derive secondary sub-states (like counting categories or sub-filtering the pool) from that pre-computed, memoized result to eliminate the O(N) duplicate processing overhead.
