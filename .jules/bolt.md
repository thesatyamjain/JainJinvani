## 2024-05-23 - Debouncing Search Overlay Queries
**Learning:** In the `SearchOverlay` component, filtering content directly on every keystroke (`query`) blocks the main thread because the calculation of `categoryCounts` and `filteredItems` are synchronous and depend directly on the query state. This leads to input lag and UI stuttering on low-end devices.
**Action:** Debounced the search `query` value and replaced instances of `query` in heavy operations (like `categoryCounts`, `filteredItems` and complex UI logic) with `debouncedQuery`. This allows the input state to update instantly while deferring expensive operations to slightly later, making the UI feel smoother.
## 2024-05-24 - Memoizing Ranked Results in SearchOverlay
**Learning:** Even though the search query in `SearchOverlay.tsx` was debounced, computing `searchAndRankItems(allItems)` redundantly multiple times in separate `useMemo` blocks (one for `categoryCounts` via `matchSearchQuery` loop, and one for `filteredItems`) caused unnecessary O(N) recalculations on every input change or tab switch, leading to main thread blocks.
**Action:** When filtering or counting a master dataset, compute the base filtered dataset once per dependency (e.g., query) and memoize it. Derive sub-states (like counts or tab-specific slices) from the already-memoized subset instead of reiterating the master list.
